# Secret 및 환경변수 관리 규칙

## 1. 목적과 적용 범위

이 문서는 로컬 개발, Docker Compose, CI/CD 및 배포 환경에서 환경변수와 Secret을
안전하고 일관되게 관리하기 위한 저장소 기준이다. 모든 서비스와 자동화 스크립트에
적용하며, 구체적인 변수 목록은 각 서비스의 `.env.example`과 README에서 관리한다.

환경변수는 실행 환경에 따라 달라지는 설정값이고, Secret은 외부에 공개되면 안 되는
인증정보 또는 민감정보다. API Token, 비밀번호, Private Key, 인증서의 개인키와 접근
Credential은 모두 Secret으로 취급한다.

## 2. 기본 원칙

- 실제 Secret은 코드, Git 이력, `.env.example`, 문서, 이슈 및 {{pr_noun}}에 기록하지 않는다.
- 로컬 값은 Git에서 제외된 `.env` 계열 파일에만 저장한다.
- 저장소에는 변수 이름과 용도를 설명하는 `.env.example`만 커밋한다.
- CI/CD와 배포용 Secret은 {{ci_variables}} 등 저장소 밖의 승인된 저장소에서 주입한다.
- 애플리케이션은 Secret을 소스 코드의 기본값으로 제공하지 않는다. 필수 Secret이 없으면
  명확한 오류와 함께 실행을 중단한다.
- Secret을 로그, 오류 메시지, 테스트 결과, 스크린샷 및 AI 프롬프트에 출력하지 않는다.
- Git ignore는 실수 방지를 위한 보조 수단이며, 커밋 전 변경 파일과 이력을 직접 확인한다.

## 3. 환경별 보관 및 주입

| 환경 | 일반 설정 | Secret | 저장소 포함 여부 |
| --- | --- | --- | --- |
| 로컬 개발 | 개인 `.env` | 개인 `.env` | 포함하지 않음 |
| 예시 및 문서 | `.env.example` | 값 없이 이름과 설명만 기록 | 포함 |
| Docker Compose 개발 | 호스트 환경 또는 개인 `.env`에서 변수 치환 | 개인 `.env`에서 주입 | 포함하지 않음 |
| CI/CD | {{ci_variables}} | 보호·마스킹한 변수 | 포함하지 않음 |
| 배포 환경 | 배포 환경의 승인된 설정 저장소 | 승인된 Secret 저장소 | 포함하지 않음 |

운영 Secret을 서버의 평문 파일로 관리하는 방식은 기본값으로 채택하지 않는다. 서버와
배포 구조가 확정될 때 접근 권한, 갱신, 감사 및 백업 방법을 함께 합의한다.

## 4. 이름과 파일 규칙

- 변수 이름은 대문자 `SNAKE_CASE`를 사용한다.
- 서비스 전용 변수는 충돌 가능성이 있으면 서비스 이름을 접두사로 사용한다.
- 공개 가능한 클라이언트 빌드 변수도 Secret과 명확히 구분한다. 브라우저 번들에 포함되는
  값에는 Secret을 넣지 않는다.
- 루트 `.env.example`은 저장소 공통 도구의 변수만 관리한다.
- 서비스 변수는 해당 서비스 디렉터리의 `.env.example`에서 관리한다.
- `.env`, `.env.local`, `.env.development` 등 실제 값을 담을 수 있는 `.env` 계열 파일은
  커밋하지 않는다.
- 새로운 환경변수를 추가하거나 이름을 변경하면 같은 작업에서 `.env.example`과 해당
  README를 함께 갱신한다.

## 5. `.env.example` 작성 기준

`.env.example`에는 다음 내용을 기록한다.

- 애플리케이션이 읽는 정확한 변수 이름
- 필수 또는 선택 여부와 용도
- Secret이 아닌 경우에만 안전한 로컬 예시값
- 값의 형식이나 허용 범위가 필요한 경우 짧은 설명

Secret 변수는 빈 값으로 두거나 `<REQUIRED>`처럼 실제 인증정보가 아닌 표식을 사용한다.
실제 도메인, 이메일, 계정 ID, 내부 IP 및 토큰과 유사한 문자열을 예시로 복사하지 않는다.

```dotenv
# Required secret. Issue a personal value and keep it only in .env.
EXTERNAL_API_TOKEN=

# Optional non-secret local setting.
BACKEND_PORT=8080
```

## 6. Docker Compose 적용 기준

- Compose 파일에는 실제 값을 직접 작성하지 않고 `${VARIABLE}` 형태로 참조한다.
- 필수 변수는 누락을 숨기는 임의의 운영 기본값을 두지 않는다.
- 개발 편의를 위한 기본값은 Secret이 아니며 모든 개발자에게 안전할 때만 사용한다.
- 컨테이너 이미지의 `ARG`, `ENV` 또는 이미지 레이어에 Secret을 저장하지 않는다.
- 빌드 과정에서 인증정보가 필요하면 이미지와 빌드 로그에 남지 않는 별도 Secret 전달
  방식을 사용하고, 적용 방식은 관련 업무 항목에서 합의한다.

## 7. CI/CD 변수 기준

- CI/CD 변수는 필요한 프로젝트와 환경에만 최소 범위로 등록한다.
- Secret은 마스킹 가능한 경우 마스킹한다.
- 보호 브랜치나 태그에서만 필요한 배포 Secret은 보호 변수로 설정한다.
- 개발, 스테이징 및 운영 값은 환경 범위를 분리하고 같은 키의 재사용 여부를 명시한다.
- CI 정의에서 Secret 값을 출력하거나 파일 내용 전체를 진단 로그로 남기지 않는다.
- 외부 Fork 또는 신뢰할 수 없는 Pipeline에 배포 Secret이 전달되지 않도록 실행 조건과
  변수 보호 설정을 함께 검토한다.
- 변수 등록·변경 권한은 최소 인원으로 제한하고, 변경 사실과 갱신 주기를 팀이 관리한다.

CI에서 AI 모델로 {{pr_noun}}을 리뷰하는 자동화를 쓰면 다음을 함께 지킨다.

- 모델 자격 증명(API 키 또는 OAuth 토큰)은 실제로 쓰는 하나만 등록한다. 리뷰 댓글용 토큰은 {{pr_noun}} 읽기와
  댓글 작성에 필요한 최소 권한의 전용 토큰으로 발급한다.
- 두 토큰 모두 보호·마스킹하고 변수 확장을 끄며, 리뷰 전용 환경 범위로만 노출한다.
- 리뷰 토큰을 {{pr_noun}} 파이프라인이나 {{pr_noun}} 소스의 스크립트와 함께 실행하지 않는다. 보호 브랜치에 고정된
  리뷰 코드만 토큰을 읽는다.
- 모델을 실행하는 자식 프로세스에는 고른 자격 증명 하나만 넘기고, 토큰과 리뷰 원문은 로그에 남기지 않는다.

## 8. 변경과 리뷰 절차

환경변수의 추가·변경·삭제는 사용하는 서비스, Docker Compose, CI/CD 및 배포 환경에 영향을
줄 수 있는 공통 계약 변경이다.

1. {{issue_noun}}에 변수 이름, 용도, 영향받는 환경과 적용 순서를 기록한다.
2. 실제 값 없이 `.env.example`과 관련 문서를 먼저 또는 같은 {{pr_noun}}에서 변경한다.
3. 병행 작업과 변수 이름 및 적용 시점을 합의한다.
4. {{pr_noun}}에서 실제 Secret, 개인 설정 및 불필요한 환경 파일이 없는지 확인한다.
5. 배포 환경의 값 변경은 롤백 방법과 서비스 재시작 필요 여부를 확인한다.

## 9. 노출 사고 대응

Secret이 Git, 로그, 이슈, {{pr_noun}}, 메신저, 문서 또는 AI 프롬프트에 노출되면 단순히
문자열을 삭제하는 것으로 끝내지 않는다.

1. 해당 Secret을 즉시 폐기하거나 비활성화한다.
2. 새로운 Secret을 발급하고 필요한 환경에만 다시 등록한다.
3. 로그와 저장소에서 노출 범위, 접근 가능자와 사용 흔적을 확인한다.
4. 서비스 영향과 대응 내용을 팀에 알린다. 공유 내용에는 Secret 원문을 다시 넣지 않는다.
5. Git 이력 정리가 필요하면 팀과 합의하고, 재작성에 따른 모든 작업 브랜치 영향을
   확인한 뒤 수행한다.
6. ignore, 권한, 로그 마스킹 또는 리뷰 절차를 보완해 재발을 방지한다.

## 10. 완료 전 점검

- 변경 파일과 Git 추적 대상에 `.env` 계열 파일이 없는가?
- `.env.example`에 실제 계정, 내부 주소 또는 Secret과 유사한 값이 없는가?
- 새 변수의 사용자, 필수 여부, 주입 환경과 적용 순서가 설명되어 있는가?
- 브라우저 번들, 컨테이너 이미지 및 CI 로그에 Secret이 포함되지 않는가?
- CI/CD 변수의 마스킹, 보호 및 환경 범위가 용도에 맞는가?
- 노출된 적이 있는 Secret을 삭제만 하지 않고 폐기·재발급했는가?
