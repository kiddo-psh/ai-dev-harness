# Git 컨벤션

## 1. 운영 원칙

- `{{default_branch}}`은 배포 및 시연 가능한 안정 버전을 유지한다.
- `{{integration_branch}}`은 팀 개발 내용을 지속적으로 통합하는 기본 브랜치다.
- 실제 개발은 {{issue_noun}} 단위의 짧은 작업 브랜치에서 진행한다.
- `{{default_branch}}`과 `{{integration_branch}}`에는 직접 Push하지 않고 {{pr_long}}를 통해서만 병합한다.
- 영역별 장기 통합 브랜치는 만들지 않는다.

```text
{{default_branch}}
  ↑  팀 합의 일정에 따라 QA 및 통합 테스트 후 병합
{{integration_branch}}
  ↑        ↑        ↑
feat/*    fix/*    refactor/*
```

## 2. 브랜치 전략

| 브랜치 | 역할 |
| --- | --- |
| `{{default_branch}}` | 배포 및 시연 가능한 안정 버전 |
| `{{integration_branch}}` | 팀 개발 결과가 합쳐지는 통합 브랜치이자 기본 브랜치 |
| 작업 브랜치 | 하나의 {{issue_noun}}을 구현하는 단기 브랜치 |

브랜치 이름:

```text
<type>/<KEY>-<description>
```

| Type | 용도 |
| --- | --- |
| `feat` | 새로운 기능 |
| `fix` | 버그 수정 |
| `refactor` | 기능 변경 없는 리팩터링 |
| `test` | 테스트 코드 |
| `docs` | 문서 수정 |
| `chore` | 기타 설정 및 작업 |
| `ci` | CI/CD 설정 변경 |

예시:

```text
feat/{{branch_key_example}}-movie-recommend
fix/{{branch_key_example}}-login-error
```

- 작업 추적을 위해 작업 브랜치에는 {{issue_key}}를 반드시 포함한다.
- 한 브랜치에는 하나의 {{issue_noun}}만 포함한다.
- 작업 브랜치는 최신 `{{integration_branch}}`에서 생성하고 가능한 1~2일 안에 병합한다.

## 3. 커밋 컨벤션

Conventional Commits 형식을 사용한다.

```text
<type>(<scope>): <내용>
```

Scope는 담당자가 아니라 실제 변경 영역(디렉터리)을 기준으로 정하고, 프로젝트 시작 시
영역 목록을 이 표에 채운다.

| Scope | 변경 영역 |
| --- | --- |
| `fe` | 프론트엔드 디렉터리 |
| `be` | 백엔드 디렉터리 |
| `infra` | 인프라 설정 |
| `docs` | 문서 |

- 여러 영역을 포괄하거나 Scope가 불필요하면 생략할 수 있다.
- 커밋 메시지에는 {{issue_key}}를 필수로 넣지 않는다.
- 제목은 변경 결과가 드러나는 명령형 표현으로 간결하게 작성한다.

## 4. {{pr_long}} 규칙

### 작업 브랜치에서 {{integration_branch}}으로 병합

제목 형식:

```text
[<KEY>] <type>(<scope>): <내용>
```

본문에는 다음 내용을 포함한다.

- `Closes <KEY>` 형식의 관련 이슈
- 변경이 필요한 배경과 병합 후 해결되는 문제
- 논리 단위로 정리한 변경 내용과 diff만으로 알 수 없는 판단 근거
- 검증 방법과 결과, 검증하지 못한 사항 및 남은 위험
- API 계약, DB Schema, 환경 변수, 의존성, CI/CD 등 공통 영역의 영향 여부
- 대안 중 선택한 결정, 리뷰 순서와 후속 작업 등 리뷰에 필요한 사항

해당 사항이 없는 선택형 절은 삭제해 형식적인 내용을 남기지 않는다. 공통 영역에 영향이
있으면 관련 영역 담당자를 리뷰어로 추가하고, 필요한 사전 합의 또는 적용 순서를 본문에
기록한다.

작업 {{pr_noun}}은 다음 원칙을 따른다.

- 하나의 {{issue_noun}} 또는 하나의 명확한 변경 목적만 포함한다.
- 본인이 만든 {{pr_noun}}을 본인이 승인하지 않는다.
- 최소 한 명의 리뷰와 Approve를 받은 후 병합한다.
- Squash를 활성화하고 병합 후 Source Branch를 삭제한다.
- CI가 구성된 이후에는 Pipeline이 성공한 상태에서만 병합한다.

### {{pr_noun}} 크기

{{pr_noun}}은 하나의 목적을 유지하고 리뷰 가능한 크기로 작성한다. 대규모 변경은 분리
가능성을 검토하고, 분리하기 어렵다면 본문에 이유와 리뷰 순서를 작성한다. 기능 구현과
무관한 대규모 리팩터링은 같은 {{pr_noun}}에 섞지 않는다.

테스트 코드를 제외한 수동 구현 변경량을 400줄 이내로 작성하는 것을 권장한다. 400줄을
초과하면 기능 또는 계층별 분할을 검토하고, 600줄을 초과하면 분할을 원칙으로 한다.
생성 코드, 의존성 및 lock 파일, 자동 포맷 변경은 수동 구현 변경량에서 제외하지만 전체
리뷰 부담에는 포함한다. 분할하면 미완성 계약이 노출되거나 같은 변경을 반복해야 하는 등
분리가 더 위험한 경우에는 예외를 허용하고, 본문에 합쳐야 하는 이유와 리뷰 순서를 작성한다.

### {{integration_branch}}에서 {{default_branch}}으로 병합

- 팀장이 팀 합의 일정에 따라 통합 {{pr_noun}}을 진행한다.
- QA와 통합 테스트를 통과한 `{{integration_branch}}`만 `{{default_branch}}`으로 병합한다.
- 예정된 통합일이라도 빌드·테스트가 실패하거나 시연 가능한 상태가 아니면 병합을 보류한다.
- 통합 {{pr_noun}}에는 {{issue_key}}를 제목에 강제하지 않는다.
- 생성 시 `Release.md` 템플릿을 직접 선택한다.
- Squash를 사용하지 않고 Merge commit을 생성해 업무 단위 커밋 이력을 유지한다.

## 5. 개발 환경 규칙

텍스트 파일은 저장소와 워킹트리 모두 LF를 사용한다. 루트 `.gitattributes`가 이를
강제하므로 운영체제와 개인 git 설정에 관계없이 동일하게 동작한다. Windows 배치 파일만
CRLF를 쓰고 바이너리는 변환하지 않는다.

Windows용 git은 설치 시 `core.autocrlf=true`가 들어간다. 내용이 같은데도 수정하지 않은
파일이 `git status`에 다수 나타나면 개행문자 문제를 의심한다.

```bash
git config --global core.autocrlf false
git diff --stat --ignore-cr-at-eol   # 비어 있으면 개행문자만 다른 상태
```

## 6. 규칙 변경

- 이 문서를 Git 협업 규칙의 기준 문서로 사용한다.
- 외부 문서는 핵심 내용을 요약하고 이 문서로 연결한다.
- 규칙 변경도 {{issue_noun}}과 {{pr_noun}}을 통해 팀 리뷰를 받은 뒤 반영한다.
