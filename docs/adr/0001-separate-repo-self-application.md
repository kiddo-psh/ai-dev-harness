# ADR-0001: 키트는 별도 공개 저장소에서 만들고 자신에게 먼저 적용한다

| 항목 | 값 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-09-29 |
| 결정자 | 박시현 |
| 관련 | roadmap 6장 원칙 |

## 맥락

feelm 저장소에는 AI 작업 절차(AGENTS.md 3층, 플랜·리뷰 게이트, Claude MR 리뷰 러너)가 있지만 도메인
이름과 경로가 박혀 있어 다음 프로젝트에서 복사하면 다시 손질해야 한다. feelm은 팀 저장소이고 업무
항목 하나에 브랜치 하나라는 규칙이 있어 키트 개발을 그 안에서 할 수 없다. 키트를 AI로 만들면 키트
저장소에도 규칙 파일이 필요해 순환이 생긴다.

## 결정

키트는 GitHub의 별도 공개 저장소 `ai-dev-harness`에서 만든다. feelm 파일은 읽기만 하고 복사해 오며
feelm을 수정하지 않는다. 키트 저장소의 루트 규칙 파일은 손으로 쓰지 않고 `core/templates/`에서
`init --self`로 생성하며, CI가 드리프트를 검사한다. 만들어지는 기능(hooks, 판정, 보안 CI, 측정)은
완성 즉시 키트 저장소에 적용한다.

## 고려한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| A (선택) 별도 저장소 + 자기 적용 | 이력이 처음부터 키트에 쌓임, 키트가 첫 사용자가 되어 불편을 일찍 발견 | 루트 파일과 템플릿 두 벌 관리 필요 → 드리프트 검사로 해결 |
| B feelm 안 `tools/harness/`에서 개발 후 추출 | 기존 규칙과 CI를 바로 씀 | 팀 저장소 오염, 이력 단절, 공개 전환 시 비식별화 부담 |
| C 키트 저장소에 규칙 없이 개발 | 순환 없음 | 키트를 만드는 세션이 키트의 규칙을 받지 않아 첫 사용자 관찰이 사라짐 |

## 결과

- **얻는 것**: 공개 이력, 첫날부터의 dogfooding, 규칙 파일의 단일 원천
- **감수하는 것**: 템플릿 수정 → 재생성 → 검증의 한 단계 추가
- **후속 작업**: 이관 문서에 대해 팀에 알리고 feelm 고유 내용 제거를 이관 대장으로 추적
